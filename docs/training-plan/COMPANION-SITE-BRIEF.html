    FlowRunner Training Companion Site — Build Brief¶

    Working name: Tulip & Twine — a small fictional e-commerce shop (the running-example company from the FlowRunner training program, made real). Name is a placeholder; keep it easily changeable (one constant).

    What this is: an open-source site that plays the entire periphery for FlowRunner training tutorials. Learners never build test harnesses, fake APIs, or webhook receivers — the site provides all of it, out of the box, with real-world fidelity. The learner's time goes 100% into FlowRunner.

    What this is not: a marketing or demo asset, a FlowRunner-branded property, or a general webhook-testing tool. Training only. No accounts, no real payments, no real emails.

    Stack (decided): pure HTML/JS front end (no framework, no build step) on Cloudflare Pages + Pages Functions (Workers) for all dynamic behavior. Durable Objects for per-sandbox state and delayed callbacks (DO alarms). Verify current free-plan limits for DO/SQLite storage before finalizing; if a feature requires a paid plan, note it in the README rather than silently depending on it.

    1. Product principles¶

    1. Realism is the quality bar. Payloads, latencies, and failure modes must resemble what learners will meet at work: Stripe/Shopify-like JSON shapes, amounts in cents, ISO-8601 timestamps, paginated lists, occasional 429s and timeouts. Nothing that looks like {"foo": "bar"}.
    2. Every page teaches transparently. Each scenario page includes a "What just happened" panel showing the exact HTTP exchange (method, URL, headers, body — sent and received), with a copy-as-curl button. The site is itself an instrument for understanding HTTP.
    3. Zero setup. First visit generates a sandbox; the learner pastes FlowRunner URLs into a settings drawer and goes. No signup, no email, no docs-reading prerequisite.
    4. Fail on purpose, deterministically when asked. Failure injection exists to serve the error-handling lessons and must be reproducible (a lesson can say "set Inventory to fail twice then succeed" and every learner sees the same behavior).
    5. The site maps to the curriculum, not the other way round. Every page exists because a course exercise needs it. A TUTORIAL-MAP.md in the repo maintains the page ↔ course/lesson mapping (mirrors the training program's traceability matrix).

    2. Learner and sandbox model¶

    • Sandbox token: on first visit, generate a short token (e.g. 10 chars, unambiguous alphabet), store in localStorage, display in the site header. All server-side state is keyed by it. A "Reset sandbox" control issues a new token.
    • State TTL: all sandbox state expires 7 days after last write. Nothing is permanent.
    • Settings drawer (client-side): one place to paste per-scenario FlowRunner URLs — form trigger URL, checkout trigger URL, shipping-quote Call Flow URL, support-agent Call Flow URL. Stored in localStorage only; the server never persists learner URLs except inside a queued callback job, which is deleted after delivery. Each scenario page reads its URL from settings and shows a friendly configured/not-configured state with a link to the relevant lesson.
    • No PII: form inputs are relayed to the learner's own flow and never stored server-side. Seed data uses .test/example.com addresses only.

    3. Scenario surfaces (mapped to courses)¶

    3.1 Contact page — FR-101¶

    A realistic "Contact Us" page for the shop. On submit, POST the submission as JSON to the learner's configured form-trigger URL. Show the response status and body in the transparency panel. Empty state explains what to configure and links to the FR-101 lesson.

    Payload: 

    {
  "type": "contact.submitted",
  "submitted_at": "2026-08-24T17:41:03Z",
  "name": "…", "email": "…", "topic": "order|product|other", "message": "…"
}

    3.2 Shop APIs — FR-102 / FR-103¶

    Read-only REST APIs over seeded, per-sandbox data (~40 products, ~120 orders, ~30 customers; regenerated on sandbox reset with slight variation).

    • GET /api/{token}/products · GET /api/{token}/orders · GET /api/{token}/orders/{id} · GET /api/{token}/customers
    • Pagination: ?page= / ?limit= with X-Total-Count and RFC-5988 Link headers (List Iterator lessons).
    • Order shape (canonical): 
      {
  "id": "ord_8h2k1x", "created_at": "2026-08-21T09:14:22Z", "status": "paid",
  "currency": "USD",
  "customer": { "id": "cus_ali01", "name": "Alice Nguyen", "email": "alice@example.test" },
  "shipping_address": { "line1": "…", "city": "…", "region": "…", "postal_code": "…", "country": "US" },
  "line_items": [ { "sku": "TT-VASE-M", "title": "Ceramic vase (medium)", "quantity": 2, "unit_price_cents": 2450 } ],
  "subtotal_cents": 4900, "shipping_cents": 799, "tax_cents": 417, "total_cents": 6116
}
    • Legacy endpoint GET /api/{token}/legacy/orders: same data, deliberately messy — inconsistent key casing, numbers as strings, nulls, dates in MM/DD/YYYY, one flat denormalized shape. Exists solely for Transform Data lessons.

    3.3 Flaky Inventory service — FR-103¶

    GET /api/{token}/inventory/{sku} with a per-sandbox failure profile set via a small control page (and via query params for lesson reproducibility): - Modes: fail_rate (0–1), fixed latency_ms ± jitter, and deterministic scripts (fail_next=2, timeout_next=1, rate_limit_next=1 → 429 with Retry-After). - Errors are realistic: 500 with JSON error body, 429, hard timeout (respond after > learner-side timeout), occasional malformed JSON mode.

    3.4 Checkout — FR-104¶

    A storefront checkout (cart seeded from products). Two integration points: 1. Order submission: on place-order, POST an order.created event to the learner's checkout trigger URL. 2. Shipping quote (the payoff moment): a "Get shipping quote" step calls the learner's Call Flow blocking endpoint with the cart payload and renders the returned result directly in the checkout UI. The learner's Return Result block visibly drives a real page. Handle timeout (30 s) and non-2xx gracefully with the transparency panel showing what happened.

    3.5 Approvals Desk — FR-104 (external callbacks / human-in-the-loop)¶

    Implements the docs' "system accepts a callback address per request" pattern: - POST /api/{token}/approvals with { "title", "details", "callback_url" } — called by the learner's flow when it pauses on an External Callback (the flow composes callback_url including its execution id). - The Approvals Desk page lists pending requests with Approve / Reject buttons and an optional comment. Decision → site POSTs to callback_url: 

    { "decision": "approved", "approver": "Dana (Ops Manager)", "comment": "…", "decided_at": "…" }
    - Auto mode per sandbox: auto-approve or auto-reject after N seconds (DO alarm) so async lessons work without a second person.

    3.6 Payments simulator — FR-104¶

    POST /api/{token}/payments with { "order_id", "amount_cents", "callback_url" } → immediate 202 { "payment_id", "status": "pending" }, then 5–30 s later a webhook to callback_url (DO alarm), weighted ~85% succeeded / 15% failed (deterministic override: outcome=failed, delay_seconds=): 

    {
  "id": "evt_9k2m…", "type": "payment.succeeded", "created_at": "…",
  "data": { "payment_id": "pay_7f…", "order_id": "ord_8h2k1x", "amount_cents": 6116, "status": "succeeded", "failure_reason": null }
}
    - Include an X-Signature header (HMAC-SHA256 of body, keyed by sandbox token) on all outbound webhooks. Lessons may ignore it; its presence is realism, and an advanced lesson can teach verification.

    3.7 Knowledge pack + Support chat — FR-105¶

    • Knowledge pack: downloadable shop content for Knowledge Base lessons — product FAQ, returns policy, shipping policy, care guides (markdown + PDF). Written to contain specific, checkable facts so an agent's grounded answers are verifiable ("returns accepted within 45 days").
    • Support chat widget: a chat page that POSTs { "customer_id", "customer_name", "message" } to the learner's agent Call Flow (blocking) URL and renders the reply. Persona switcher (Alice / Bob / guest) changes customer_id — exists to demonstrate per-user memory anchoring: the agent should remember Alice's conversation but not leak it to Bob.

    3.8 Traffic generator — FR-106¶

    "Simulate a business day": emits a bounded stream of events (orders + contact submissions) to the learner's configured URLs — max 50 events, min interval 5 s, one run active per sandbox — to populate Monitoring/Performance dashboards and create realistic failures to find. Protected by Cloudflare Turnstile (the only expensive endpoint).

    4. Security and abuse (non-negotiable before public deploy)¶

    The site makes outbound HTTP to user-supplied URLs; treat it as a potential open relay and constrain it: - Outbound URL rules: https:// only; hostname must not resolve to private/link-local/loopback ranges; no IP-literal hosts; redirects not followed; 10 s timeout; response bodies capped (64 KB) before display; identifying User-Agent: TulipTwine-TrainingSim/1.0 (+repo URL). - Rate limits: per-sandbox and per-IP caps on every outbound-calling endpoint (Cloudflare rate-limiting rules + in-DO counters). Traffic generator additionally gated by Turnstile and the 50-event cap. - Payload caps: inbound request bodies capped (e.g. 32 KB); reject files/uploads entirely. - No stored learner URLs beyond pending callback jobs (deleted on delivery or 24 h, whichever first). No logs containing form field values. - Abuse contact in README and in the outbound User-Agent.

    5. Repo and deployment¶

    • MIT license. Root: README.md (what it is, one-click Deploy to Cloudflare button, local dev via wrangler pages dev), TUTORIAL-MAP.md, CONTRIBUTING.md, wrangler.toml, /public (static pages), /functions (Pages Functions), /seed (data generators), /knowledge-pack.
    • Self-hosting is first-class: a learner or company must be able to fork and deploy their own instance in minutes (this is also the escape hatch for anyone whose FlowRunner endpoints the hosted instance's URL rules would block).
    • No analytics beyond Cloudflare's own aggregate metrics.

    6. Build phases (aligned to course rollout)¶

    Phase Ships with Contents
    A FR-101 Site shell, sandbox model, settings drawer, transparency panel, Contact page, shop APIs incl. legacy endpoint
    B FR-103/104 Flaky Inventory + control page, Checkout (order event + shipping quote), Approvals Desk, Payments simulator, webhook signing
    C FR-105/106 Knowledge pack, Support chat + personas, Traffic generator, Turnstile

    Each phase lands with acceptance checks (below) green and TUTORIAL-MAP.md updated.

    7. Acceptance checks (curl-able, per feature)¶

    1. New visit issues a sandbox token; GET /api/{token}/orders?limit=5 returns 5 orders with pagination headers; legacy endpoint returns the same order recognizably mangled.
    2. Contact submit POSTs the documented payload to a configured URL and surfaces the response in the transparency panel; unconfigured state renders the guidance card.
    3. Inventory with fail_next=2 fails exactly twice with a 500 JSON body, then succeeds; 429 mode includes Retry-After.
    4. Checkout shipping quote renders the body returned by a stub blocking endpoint; a 30 s-silent stub produces the timeout UI, not a hang.
    5. POST /approvals appears on the Desk; Approve delivers the decision payload to the callback URL within 2 s; auto mode delivers after the configured delay.
    6. Payment callback arrives 5–30 s later with a valid X-Signature; outcome=failed&delay_seconds=6 behaves deterministically.
    7. Outbound calls to http://…, https://10.0.0.1/…, https://localhost/…, and a 30-redirect URL are all refused with a clear error shown to the learner.
    8. Traffic generator refuses a second concurrent run and stops at 50 events.
    9. A fresh fork deploys to Cloudflare Pages from the README instructions alone.

    8. Explicitly out of scope¶

    Accounts and auth for learners; real payment/email providers; persistence beyond the 7-day sandbox TTL; FlowRunner branding (this is the fictional shop's site); marketing/landing content; multi-language; mobile apps.
